A Graph cleanup that "worked yesterday" can stop at midday and take the rest of the day's wipes with it.

Portal clicks, [bulk device actions](https://learn.microsoft.com/en-us/intune/device-management/actions/), and Microsoft Graph share one tenant counter per action. Graph is not a side channel.

## One Counter Per Action. Three Ways To Spend It.

[Daily tenant limits](https://learn.microsoft.com/en-us/intune/device-management/actions/#daily-tenant-limits):

| Action | Per tenant per day |
| --- | --- |
| [Wipe](https://learn.microsoft.com/en-us/intune/device-management/actions/wipe) | 500 |
| [Retire](https://learn.microsoft.com/en-us/intune/device-management/actions/retire) | 1,000 |
| [Delete](https://learn.microsoft.com/en-us/intune/device-management/actions/delete) | 1,000 |

Each count is cumulative across single-device actions, bulk (up to 100 devices per request), and Graph. Raise a limit through [Microsoft support](https://learn.microsoft.com/en-us/intune/fundamentals/it-pro-support/get-support-admin-center). Learn does not document when the day resets.

Help desk wipes, a school-year bulk reset, and a stale-device script all spend the same 500.

## The Cap Is A Blast Radius. Not Graph Throttling.

Learn publishes the numbers. It does not publish a motive.

It does publish the class of command. [Retire, Wipe, and Delete take precedence](https://learn.microsoft.com/en-us/intune/device-management/actions/) over every other pending action. Queue one of those and the rest are ignored. [Wipe](https://learn.microsoft.com/en-us/intune/device-management/actions/wipe) factory-resets. You do not want that unbounded.

The counter is tenant-wide on purpose. A portal click, a bulk of 100, and a Graph call all spend it. Graph is not a side channel. [Support can raise a limit](https://learn.microsoft.com/en-us/intune/fundamentals/it-pro-support/get-support-admin-center). That is a tenant rail you can petition, not a hard architecture ceiling.

This next part is ours, not Microsoft's. A compromised admin, a bad `foreach`, and a school-year reset job compete for the same 500. The cap is the last brake after RBAC already let the call through. It is not Graph [throttling](https://learn.microsoft.com/en-us/graph/throttling). No `429`. No `Retry-After`.

## Eighty Thousand Wipes In One Morning

[Stryker, March 11, 2026](https://www.bleepingcomputer.com/news/security/stryker-attack-wiped-tens-of-thousands-of-devices-no-malware-needed/): a compromised admin, a new Global Administrator, and the Intune wipe command. A source familiar with the attack put it at nearly 80,000 devices between 05:00 and 08:00 UTC. Investigators found no indication of exfiltration. Stryker said no malware, medical products unaffected, internal Microsoft environment only.

Today's published cap is 500 Wipes per tenant per day. If that cap had been enforcing that morning, the run stops at 500, not 80,000. That is arithmetic, not a leak.

[CISA's public answer](https://www.cisa.gov/news-events/alerts/2026/03/18/cisa-urges-endpoint-management-system-hardening-after-cyberattack-against-us-organization), with Microsoft and Stryker contributing, was least-privilege RBAC, phishing-resistant MFA, and Multi Admin Approval for high-impact actions such as device wiping. Not a quota. MAA is a second human. A quota is a platform brake after the call is already authorized. CISA does not mention a daily wipe limit.

A July 7, 2026 Wayback capture of Learn's device-actions page still had the precedence note and the bulk-of-100. It did not have the 500 / 1,000 / 1,000 table. Learn published those tenant-wide daily caps in August 2026. That is when the docs became public. It is not a Microsoft admission of when enforcement started.

This is speculation, not a Microsoft statement. Microsoft has not said the cap is a Stryker patch. The sequence and the math are why it is a reasonable operator guess that a tenant-wide daily wipe brake showed up after someone used Intune as a fleet kill switch.

## Android Delete Is A Wipe. It Still Counts.

[Delete](https://learn.microsoft.com/en-us/intune/device-management/actions/delete) is not inventory-only.

Windows, Apple, macOS, Android Device Administrator, and personally owned work profile Delete trigger Retire.

Android corporate-owned fully managed (COBO), dedicated (COSU), corporate-owned work profile (COPE), and AOSP Delete trigger **Wipe**. That is a device command, not a record cleanup. On most of those platforms Wipe is a factory reset. [Learn's Wipe page](https://learn.microsoft.com/en-us/intune/device-management/actions/wipe) calls out Zebra: Wipe removes corporate data and does not factory-reset.

The Delete daily limit still applies when Delete triggers Retire or Wipe. A Graph `DELETE` against those Android types spends Delete quota and wipes the device. Learn does not say the triggered Wipe also increments the 500 Wipe counter. Budget the Delete. Treat the device as wiped.

## Graph Calls The Same Actions

Success is `204 No Content` on all three.

```http
POST   /deviceManagement/managedDevices/{managedDeviceId}/wipe
POST   /deviceManagement/managedDevices/{managedDeviceId}/retire
DELETE /deviceManagement/managedDevices/{managedDeviceId}
```

[wipe](https://learn.microsoft.com/en-us/graph/api/intune-devices-manageddevice-wipe?view=graph-rest-1.0) and [retire](https://learn.microsoft.com/en-us/graph/api/intune-devices-manageddevice-retire?view=graph-rest-1.0) need

`DeviceManagementManagedDevices.PrivilegedOperations.All`

[delete](https://learn.microsoft.com/en-us/graph/api/intune-devices-manageddevice-delete?view=graph-rest-1.0) needs

`DeviceManagementManagedDevices.ReadWrite.All`

There is no documented Graph API or header for remaining daily quota. Preflight is the size of the list you are about to submit. [Devices > Device actions](https://learn.microsoft.com/en-us/intune/device-management/actions/#check-the-status-of-the-action) is status, not remaining quota.

Graph [throttling](https://learn.microsoft.com/en-us/graph/throttling) is a different limit: HTTP `429`, `TooManyRequests`, often `Retry-After`. The daily action-limit failure shape is not documented. Do not assume 429, 400, or 403 means the 500 is gone. Log it and stop.

## Don't Run Unbounded Foreach Wipes

```powershell
$requiredScopes = @(
    'DeviceManagementManagedDevices.ReadWrite.All',
    'DeviceManagementManagedDevices.PrivilegedOperations.All'
)
Connect-MgGraph -Scopes $requiredScopes -NoWelcome

$wipeDailyCap = 500
$runCap = 50
$spent = 0
$results = [System.Collections.Generic.List[pscustomobject]]::new()

foreach ($device in $targets) {
    if ($spent -ge $runCap) {
        break
    }

    $uri = "https://graph.microsoft.com/v1.0/deviceManagement/managedDevices/$($device.id)/wipe"
    $row = [pscustomobject]@{
        DeviceId   = $device.id
        DeviceName = $device.deviceName
        Action     = 'wipe'
        StatusCode = $null
        Outcome    = $null
        Detail     = $null
    }

    try {
        $null = Invoke-MgGraphRequest -Method POST -Uri $uri -Body @{ keepUserData = $false } -ContentType 'application/json'
        $row.StatusCode = 204
        $row.Outcome = 'submitted'
        $spent++
    }
    catch {
        $statusCode = $null
        if ($_.Exception.Response) {
            $statusCode = [int]$_.Exception.Response.StatusCode
        }
        $row.StatusCode = $statusCode
        $row.Detail = $_.Exception.Message
        $row.Outcome = if ($statusCode -eq 429) { 'graph-throttled' } else { 'failed' }
        $results.Add($row)
        break
    }

    $results.Add($row)
}

$results
Write-Output "Wipe actions submitted this run: $spent of $runCap. Tenant daily cap is $wipeDailyCap."
```

`$targets` is a list you built and reviewed. Retire is `POST .../retire` with no body. Delete is `DELETE .../managedDevices/{id}`. Same cap-and-stop. Same log.

If the catch is not a documented `429` throttle, do not retry it as one. You will not get a remaining-quota integer back.

## Checklist

- Count planned Wipe, Retire, and Delete before the run. Cap under 500 / 1,000 / 1,000. There is no remaining-quota API.
- Do not `foreach` wipe or delete an unbounded stale-device query.
- Split Android corporate Delete from Windows/Apple Delete. COBO, COPE, COSU, and AOSP Delete trigger Wipe and still spend Delete quota.
- Log every submit. You cannot query remaining quota later.
- On `429`, treat it as Graph throttling. On any other failure, stop. Do not guess the daily-limit status code.
- Need more than the published caps? Support request.
