## The Early Days: High Potential, High Friction

When [ChatGPT](https://chatgpt.com/) first came out, it was obvious it could boost productivity.

But the workflow sucked.

I was constantly:

- Copying code from chat → pasting into my IDE  
- Running it  
- Copying errors back into chat  
- Repeating the loop  

It worked, but it didn't scale. The friction killed it.

So I limited myself to small things:

> "Write me a function"  
> "Fix this block of code"

Anything bigger wasn't worth the effort.

---

## The Real Bottleneck: Context

The problem wasn't intelligence.

It was context.

I write [PowerShell modules](https://learn.microsoft.com/en-us/powershell/scripting/developer/module/how-to-write-a-powershell-script-module) with dozens of files. There was no realistic way to:

- Paste everything into chat  
- Maintain context across messages  
- Ensure nothing important was omitted  

And if you missed something?

The model would confidently give you the wrong answer.

Not because it was dumb-but because you gave it incomplete information.

---

## What Changed Everything

[CLI-based coding agents](https://docs.github.com/en/copilot/using-github-copilot/using-github-copilot-in-the-command-line) changed the game.

Now the LLM lives:

- Inside your repo  
- Inside your working directory  
- With full context  

Instead of asking:

> "Help me write this function"

You can say:

> "Here's a repo. Let's extend it, add features, and automate it end-to-end."

That's a completely different level of leverage.

---

## My Workflow (Step-by-Step)

This is the actual process I follow.

---

### 1. Start With a Real Problem

Look for something:

- Repetitive  
- Annoying  
- Time-consuming  

Example:

> "Setting up a new Intune tenant takes hours."

That becomes:

> "Can this be automated?"

---

### 2. Use the LLM to Define the Problem

I don't jump straight into coding.

I tell the LLM:

> "Interview me until you fully understand what I want."

Humans are bad at writing complete specs. The LLM helps uncover:

- Edge cases  
- Inputs and outputs  
- Expected behavior  
- Constraints  

I often respond using voice ([Superwhisper](https://superwhisper.com/)) to move faster.

The goal:

> Turn a vague idea into a clear requirements document.

---

### 3. Start Small

Do not boil the ocean.

Example from my [Intune Hydration Kit](https://intunehydrationkit.com/):

> "Can we import dynamic device groups from JSON?"

That's it.

Then:

- Make it work  
- Clean it up  
- Expand gradually  

---

### 4. Build in a Tight Loop

My workflow looks like this:

```
idea → branch → change → test → debug → fix → merge → repeat
```

LLMs are part of the loop-but they're not in control.

---

### 5. Always Add These Early

#### Unit Tests

- Validate behavior  
- Prevent regressions  
- Give the LLM feedback signals  

#### Debug Logging

- Critical for troubleshooting  
- Lets you feed runtime data back into the LLM  

Without these, you're guessing.

---

### 6. Constrain the LLM

LLMs overengineer by default.

So I:

- Keep things simple  
- Remove unnecessary abstractions  
- Simplify before committing  

If you don't do this, your project will bloat quickly.

---

### 7. Provide Relevant Context

The more targeted your context, the better the output.

Examples:

- PowerShell module → enforce PowerShell best practices  
- UI work → provide design references  

This is where skills become useful. Instead of rewriting the same context every time, I can reach for targeted instructions:

- [Code Simplifier](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/code-simplifier/agents/code-simplifier.md) when the implementation works but needs to be made smaller and clearer  
- [PowerShell Code Review](https://github.com/jorgeasaurus/agent-skills/blob/main/powershell-code-review/SKILL.md) when I want a production-readiness review of a script or module  
- [Frontend Design](https://github.com/anthropics/skills/blob/main/skills/frontend-design/SKILL.md) when the project needs an actual design pass instead of default AI UI  
- [Graph.pm](https://graph.pm/) when I need Microsoft Graph context close at hand  

Generic prompts produce generic output.

---

### 8. Iterate Relentlessly

This is not:

> "Generate once and done"

This is:

> Loop until it works

You will:

- Correct bad assumptions  
- Fix logic  
- Refine behavior  

That's the job.

## Case Study: [Intune Hydration Kit](https://intunehydrationkit.com/)

This workflow led to a real project.

A [PowerShell module](https://github.com/jorgeasaurus/Intune-Hydration-Kit) that:

- Bootstraps new Intune tenants  
- Applies best-practice configurations  
- Imports 800+ items  
- Produces repeatable environments  

### Outcome

- 700+ downloads via [PowerShell Gallery](https://www.powershellgallery.com/packages/IntuneHydrationKit)
- Saves hours of manual setup
- Website with hundreds of visitors per month  

The LLM didn't build it for me.

It helped me:

- Move faster  
- Iterate quickly  
- Explore ideas  

The vision and constraints were still mine.

---

## The Rule Most People Ignore

> You can outsource your thinking.  
> You cannot outsource your understanding.

If you don't understand:

- The language  
- The architecture  
- The expected behavior  

You will ship broken things confidently.

---

## Where This Still Falls Short

### 1. Cost

- Long sessions = high token usage  
- Can get expensive over time  

Alternatives exist, but it's still a tradeoff.

---

### 2. UI/UX Is Still Weak

LLMs:

- Default to generic designs  
- Reuse the same styles  
- Miss subtle UX issues  

To get good results, you need:

- Explicit instructions  
- Reference designs  
- Screenshots  
- Iteration  

Humans are still better here.

---

### 3. It Requires Discipline

If you skip:

- Requirements  
- Tests  
- Logging  

This falls apart quickly.

The workflow works because of the structure-not despite it.

---

## Final Thought

LLMs didn't just make me faster.

They changed what I'm willing to attempt.

Before:

- Small scripts  
- Isolated problems  

Now:

- Full modules  
- Real tools  
- Open source projects  

The difference isn't just productivity.

It's scope.
