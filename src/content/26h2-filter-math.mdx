26H1 is build 28000. 26H2 is 26300.

A higher Windows build number is no longer a newer release. Any assignment filter that treats the build as a monotonic "or newer" line is wrong the moment 26H2 lands.

## The Later Release Has The Lower Build

| Version | OS build | What it is |
| --- | --- | --- |
| 23H2 | 22631 | Older branch. Full feature-update path to 26H2. |
| 24H2 | 26100 | Shared servicing branch with 25H2 and 26H2. |
| 25H2 | 26200 | Same branch. eKB from 24H2. |
| 26H2 | 26300 | Same branch. eKB from 24H2 or 25H2. Not GA as of 2026-08-19. |
| 26H1 | 28000 | Different Windows core. Ships on new silicon. Cannot eKB to 26H2. |

26H1 released 2026-02-10. 26H2 is still an Insider Experimental enablement package on 26300. It is not in the [GA release table](https://learn.microsoft.com/en-us/windows/release-health/windows11-release-information) yet. [Learn's Experimental notes](https://learn.microsoft.com/en-us/windows-insider/release-notes/experimental/preview-build-26300-9032) are explicit: those flights are 26H2 via an enablement package. Treat 26300 as the 26H2 build. The marketing name will not show up as a filter property.

24H2, 25H2, and 26H2 share a servicing branch. The version change is which features are enabled. [Microsoft's 26H2 IT Pro post](https://techcommunity.microsoft.com/blog/windows-itpro-blog/get-ready-for-windows-11-version-26h2/4529367) is the source of record. 26H1 sits on a different core. No eKB. No hop to 26H2. [Microsoft is direct](https://learn.microsoft.com/en-us/windows/whats-new/windows-11-version-26h1): first devices are Snapdragon X2. It is not an in-place update from 24H2 or 25H2. 24H2 and 25H2 remain the enterprise targets. 26H1 is a hardware exception, not the next ring.

## `-ge 10.0.28000` Is Not 26H1 And Newer

The rule people write when 26H1 ships:

```powershell
(device.operatingSystemVersion -ge 10.0.28000)
```

Label that "Windows 11 26H1 and newer" and it is already false.

`operatingSystemVersion` compares versions, not strings. `10.0.26300` is less than `10.0.28000`. A 26H2 device fails. A 25H2 device that takes the 26H2 eKB moves to 26300 and still fails.

What that rule matches today: 26H1, and nothing else in the current list.

## The Same Unbounded `-ge` Also Keeps 26H1

```powershell
(device.operatingSystemVersion -ge 10.0.26100)
```

That looks like a "24H2 or newer" servicing floor if you still believe build numbers climb with time. 26H1 is 28000, so it matches. 26H2 is 26300, so it matches too.

If the intent was "current shared servicing branch," you just included Snapdragon X2 boxes that do not take the 26H2 eKB.

Any unbounded `-ge` drawn below 28000 keeps those boxes. Any floor at 28000 drops 26H2. There is no single "or newer" line that means both "the latest annual release" and "26H1."

## Write The Builds You Mean

There is no `osBuild` property. People say "build" and mean the third octet of `10.0.<build>.<revision>`.

`osVersion` is a string and it is being deprecated. No `-ge`. `operatingSystemVersion` is the replacement. Public preview. Version operators. Comparison is major.minor.build.revision. The fourth part is the monthly quality revision. Do not pin a baseline to it unless you intend to chase KB numbers.

A three-part value such as `10.0.26300` is `10.0.26300.0`. That is the right floor for a build. The matching upper bound is the next build number, not the next marketing version.

**26H2 only:**

```powershell
(device.operatingSystemVersion -ge 10.0.26300) and (device.operatingSystemVersion -lt 10.0.26301)
```

**26H1 only:**

```powershell
(device.operatingSystemVersion -ge 10.0.28000) and (device.operatingSystemVersion -lt 10.0.28001)
```

**Shared servicing branch, no 26H1** (24H2, 25H2, and 26H2):

```powershell
(device.operatingSystemVersion -ge 10.0.26100) and (device.operatingSystemVersion -lt 10.0.26301)
```

`28000` is not less than `26301`. The upper bound drops 26H1 without a second clause. That is the useful side of the broken numbering.

**26H1 or 26H2.** There is no one `-ge` for this. OR two bounded ranges:

```powershell
((device.operatingSystemVersion -ge 10.0.26300) and (device.operatingSystemVersion -lt 10.0.26301)) or ((device.operatingSystemVersion -ge 10.0.28000) and (device.operatingSystemVersion -lt 10.0.28001))
```

Do not use `arm64` as a synonym for 26H1. Plenty of 24H2 and 25H2 Arm devices exist, and they eKB to 26H2.

`operatingSystemVersion` is still public preview. Filter preview may refuse. Check a few known devices against the version tuple instead of trusting a green portal badge.

## Pull The Filters You Already Have

```powershell
Connect-MgGraph -Scopes "DeviceManagementConfiguration.Read.All" -NoWelcome

$uri = "https://graph.microsoft.com/beta/deviceManagement/assignmentFilters"
$filters = [System.Collections.Generic.List[object]]::new()
do {
    $page = Invoke-MgGraphRequest -Method GET -Uri $uri -OutputType PSObject
    foreach ($filter in $page.value) { $filters.Add($filter) }
    $uri = $page.'@odata.nextLink'
} while ($uri)

$filters |
    Where-Object { $_.rule -match 'osVersion|operatingSystemVersion' } |
    Select-Object displayName, platform, assignmentFilterManagementType, rule |
    Format-List
```

Flag any rule that:

- Uses `osVersion` with a `10.0.28` or `10.0.26` prefix and a comment that says "or newer."
- Uses `operatingSystemVersion -ge 10.0.28000` and claims to include later annual releases.
- Uses `operatingSystemVersion -ge 10.0.26300` with no upper bound. That includes 26H1.
- Pins the fourth version part unless the assignment is deliberately quality-revision specific.

Platform and management type are immutable. If the filter was created as managed apps when you needed devices, delete and recreate. You cannot PATCH your way out of that, and you cannot delete a filter that is still attached to an assignment.

## Build Number Is An Identifier

It is not a timeline.

26H1 is 28000 because it is a different core for new silicon. 26H2 is 26300 because it is an enablement package on the 24H2/25H2 branch. Intune will compare those numbers exactly as written.

Write the builds you intend to match. Bound the ones you do not. Stop asking `-ge` to invent a future that the numbering no longer describes.

## Check The Filters Before 26H2 Lands

- Unbounded `-ge 10.0.28000` is 26H1 only. It drops 26H2 at 26300.
- Unbounded `-ge` below 28000 keeps 26H1 Snapdragon X2 boxes.
- Missing upper bounds turn a build floor into every later build number, including 26H1.
- Do not pin the fourth version part unless the assignment is quality-revision specific.
- `operatingSystemVersion` is public preview. Preview the filter on a preview property before you trust a green badge.
